# Два Caddy послідовно і спільна мережа

На сервері живе кілька незалежних проектів. Порт `:443` при цьому один, тож
хтось мусить його тримати. Тримає **спільний Caddy** в окремому compose, у
зовнішній docker-мережі `web`. Кожен проект вмикається в `web` і не публікує
назовні жодного порту.

Slovnuk у цій мережі представлений **одним** контейнером — `slovnuk-frontend`,
усередині якого свій Caddy. Тобто запит проходить два Caddy поспіль: спільний
завершує TLS і віддає запит за іменем контейнера, внутрішній розводить його на
статику, `/api/*` і `/media/*`.

Увесь конфіг, який спільний Caddy знає про Slovnuk:

```caddyfile
slovnuk.ivankhomych.com {
    reverse_proxy slovnuk-frontend:80
}
```

## Чому не один Caddy

Очевидна альтернатива — спільний Caddy віддає статику сам, з тому, куди її
поклав складальник проекту. Один веб-сервер замість двох, статика з диска
замість проксі. Виглядає простіше, і на одному проекті справді простіше.

Ламається воно на другому. Ось той самий блок без внутрішнього Caddy:

```caddyfile
slovnuk.ivankhomych.com {
    handle /api/*   { reverse_proxy slovnuk-backend:8000 }
    handle /media/* { reverse_proxy slovnuk-minio:9000 }
    handle {
        root * /srv/slovnuk
        try_files {path} /index.html
        file_server
    }
}
```

Тепер спільний файл знає внутрішню будову Slovnuk: скільки в нього контейнерів,
як вони звуться, де лежить статика, що застосунок односторінковий і що аватари
йдуть повз API. Кожен наступний проект додає свій такий блок, і файл, спільний
для всіх, стає місцем, де треба розуміти кожен. Це рівно та залежність, якої
топологія мала позбутися.

Друга, менш очевидна ціна: том зі статикою оголошується в одному compose і
монтується в інший, тобто `external: true` з обох боків плюс порядок підйому —
Caddy мусить стартувати після того, як складальник поклав файли. Проксі цієї
проблеми не має взагалі: контейнера немає — спільний Caddy віддає 502, з'явився
— почав працювати.

## Розглянуті альтернативи

**Збірка на хості, `bind-mount` теки `dist`.** Відкинуто: тягне Node на сервер і
виносить артефакт збірки за межі Docker, тобто «яка версія зараз віддається»
перестає бути питанням до `docker`.

**Caddy усередині compose Slovnuk, тримає `:443`.** Тоді проект №2 проксіюється
Caddy проекту №1 — конфіг чужого проекту живе в цьому репозиторії. Незалежність
втрачається в найгрубішій формі.

**Caddy на хості, не в Docker.** Робочий варіант, і від зчеплення конфігів він
не страждає. Відкинуто через адресацію: контейнери довелося б публікувати на
`127.0.0.1` і тримати в голові реєстр «який проект узяв який номер». У мережі
`web` адресація йде іменами, і номерів немає.

## Наслідки

- **Ціна — зайвий проксі-хоп і другий веб-сервер у ланцюжку.** На обсязі
  Slovnuk (`dist` — сотні кілобайт) не вимірюється.
- **Внутрішній Caddy слухає голий `:80` без імені домену**, тому сертифікатів не
  просить: ACME вмикається саме від доменного імені в блоці. Додати туди домен
  «щоб було» означає зламати HTTPS.
- **Справжній IP клієнта** доїжджає до внутрішнього Caddy заголовком, тож у
  нього прописано `trusted_proxies static private_ranges`. Без цього логи
  показували б адресу спільного Caddy.
- **Аватари ходять через `/media/*`, а не з MinIO напряму.** Це прямий наслідок
  того, що застосунок під HTTPS: `s3.py` будує адресу з
  `S3_STORAGE_PUBLIC_ENDPOINT`, і http-адреса на https-сторінці блокується
  браузером як mixed content — без помилки в мережі й без сліду в логах.
  Завдяки проксі MinIO не публікує портів взагалі.
- **`deploy/` у цьому репозиторії — тимчасовий гість.** Спільний Caddy нічий; йому
  місце в окремому каталозі на сервері, а з появою другого проекту — в окремому
  репозиторії. Slovnuk із `deploy/` нічого не імпортує, і зворотної залежності
  теж немає.
